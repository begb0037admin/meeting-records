## 1. The two paths — pick the right one before doing anything else

PDR prep is **not one process** — it's two, depending on whose PDR it is. Getting this
wrong (treating an ask-and-build PDR as if a draft exists to verify, or vice versa)
wastes a full session. Confirm which path applies before starting.

### Path A — "verify-a-submitted-draft" (direct reports: James, Asta, Michael)

The person submits a completed draft PDR document themselves (their own self-review,
in `input\`). Lauren's job is to **read their draft and verify each claim against
sources** — Granola, email via the Codex M365 connector, command-centre, work-inbox —
flagging genuinely unsupported claims honestly rather than assuming true or false
either way. Lauren does not write their self-review content for them; she cross-checks
it and builds the meeting-prep brief (evidence, gaps, running order) around it.

Output: one HTML brief in `output\`. No separate "submittable form" — they already
have one (their own docx in `input\`).

### Path B — "ask-and-build" (Kevin's own PDR only)

Kevin has no separately submitted draft for Lauren to verify — there is no self-review
document written by someone else to read. Instead, for each standard section below,
Kevin is asked directly and supplies the actual evidence himself (pasted emails, his
own summaries, sourced facts, meeting counts) as the answer. The content is then
**built/written from his answers, one section at a time, confirmed before moving to
the next** — never inferred or pre-drafted and then corrected afterwards. This is how
Kevin's 30-Sep-2026 PDR content was actually built (see
`begb0037admin/lauren`, `memory/pdr-kevin-2026-full-content-rebuild-22sep-later.md`
and `memory/pdr-kevin-2026-30sep-confirmed-and-evidence-22sep.md` for the real session
record this process is drawn from).

**Standard per-section question to ask Kevin (Path B), one at a time:**

| # | Section | Question to ask |
|---|---------|------------------|
| 1 | Workload | "What's the real picture of your team's workload right now — where's the pressure, who's stretched, what's the burnout/capacity risk?" |
| 2 | Objectives / Performance | "Looking back over the year, what's the honest summary of your performance against your agreed objectives — what got delivered, what's still in motion, what's the evidence?" |
| 3 | Values | "Anything new to add under People / Collaboration / Quality / Continuous improvement since last year — any dated evidence (a thread, a sign-off, an application)?" |
| 4 | Development ask | "Is last year's development ask still right, or has anything changed (a route closing, a new option opening)? What's the live status?" |
| 5 | Career aspirations | "Are your career aspirations from last year still accurate, or has anything shifted — and does the development-ask answer above connect to them?" |
| 6 | Working together | "What examples from this year show how you're working with your manager and peers — anything dated and concrete, even first-pass?" |
| 7 | Single points of failure | "Is the single-points-of-failure picture from last year still accurate, or has it changed?" |
| 8 | Roadmap ownership | "Which live Roadmap items are genuinely yours right now — check against the real Roadmap/Managers Meeting docs, don't repeat last year's list unverified." |
| 9 | Close / Manager Summary | Not asked in advance — drafted post-meeting from the Granola recording (see §5). |

Each answer goes straight into **both** the brief (coaching notes / evidence) and the
actual submittable `.docx`/`.md` PDR form itself, in first person, as Kevin would
submit it — not just as talking points. If a section has no clear form field to hold
new content (e.g. "Working together" has no dedicated field in the Oxford docx
template), say so and place it under the closest genuine fit (Performance is the
established placement — see the memory entry above), flagging the placement as a
judgement call for Kevin to confirm, not a silent decision.

Output: one HTML brief **and** the generated submittable form (docx/md), both in
`output\` — Lauren wrote both, so both count as generated output, never `input\`.

## 2. Standard PDR brief sections and their intent

These are the same 8 content sections either path builds evidence for (Path A verifies
them against a submitted draft; Path B builds them from Kevin's live answers), plus the
post-meeting close:

1. **Workload** — the real day-to-day pressure picture: capacity, coverage gaps,
   burnout risk. Never a rosy default; the honest state.
2. **Objectives / Performance** — summary of performance against agreed
   objectives/priorities, grounded in dated, sourced evidence (meeting counts,
   delivery artefacts), not a vibe.
3. **Values** — People / Collaboration / Quality / Continuous improvement, each with
   real dated evidence where available.
4. **Development ask** — what training/development is being requested, and whether
   last year's ask is still live, changed, or closed off.
5. **Career aspirations** — immediate and longer-term aspirations, cross-referenced
   against the development ask so the two aren't contradicting each other.
6. **Working together** — concrete, dated examples of how the person works with their
   manager/peers/cross-team groups.
7. **Single points of failure** — where the person is the only one who can do
   something, and whether that's changed since last year.
8. **Roadmap ownership** — which live Roadmap/Managers-Meeting items this person
   genuinely owns right now, checked against the real live tracked-items docs, not
   carried forward unverified from a prior brief.
9. **Close / Manager Summary** — drafted **after** the meeting, from the Granola
   recording, not from prep content (see §5). Lands in the person's own submittable
   `.docx` review form once Kevin has reviewed the real recording.

## 3. Per-section sourcing process — pull real evidence before flagging a gap

For every section, in both paths, evidence must be **pulled and checked before**
presenting anything as an unsupported gap:

- **Granola** — full pagination, not just the first page. A real note further back in
  the list is a common miss if the search stops early.
- **Codex M365 connector (email)** — scoped to named, relevant people only, never a
  full mailbox sweep, unless Kevin explicitly asks for a broader search. **Standing
  lesson (22 Sep 2026):** scope the search to the relevant named people up front, as
  the first pass — do not run an unscoped/generic search and wait to be told twice.
  For Kevin's own PDR specifically, the people to scope to by default are: Simon
  Burford, Marie Cooksey, Emma Fitz-Gibbon, Athena, Sarah Rowles, Michael O'Sullivan
  (see `begb0037admin/lauren`, `memory/pdr-kevin-2026-30sep-confirmed-and-evidence-22sep.md`).
  For a direct report's own PDR, scope to their own manager chain and named
  collaborators, not this same list.
- **command-centre** — `data/tasks.json`, open and recently-closed tasks.
- **work-inbox** — `data/briefing.json`, `data/inbox_suggestions.json`.
- **Prior-year archive** — the person's own `archive\<year>\` docx (most recently,
  `archive\2025\`) — compare claims against what they said and were assessed on last
  year. Also check `PDR 2026 - Handover/docs/reference/` and the
  `Kevin Lelitte - Transcribed Files` local OneDrive folder for that person's actual
  prior-year PDR **meeting transcript**, which is often richer than the review-form
  docx and survives even when the docx itself is blocked (Oxford SharePoint/Edu
  permission gap — see `PDR 2026 - Handover/docs/HANDOVER.md`).
- **Prior year's signed Manager Summary priorities** — the specific named actions
  Kevin (as manager) agreed to the previous year; check whether this year's content
  visibly addresses each one, and say plainly if it doesn't.

**Flag genuinely unsupported claims honestly rather than assuming true or false either
way.** A flagged gap is always better than a plausible-sounding invention, and better
than silently treating an unverifiable claim as false. Never invent PDR content.

## 4. Output format — HTML only, no .md deliverables, ever

Standing rule, set 22 Sep 2026, applies here with full force (see Lauren's `AGENT.md`,
"Standing format rule: HTML only, no .md files"):

- **One HTML file per person**, built on `brief_chrome.py`'s shared chrome — never
  hand-designed from scratch.
- **A single running order, in meeting-stage order, at the top** — say-this / key-fact
  side by side, reusing the `rp-stage`/`rp` card CSS pattern (copy the CSS block
  verbatim from an existing brief, e.g. James Salas Guillen's or Kevin's, rather than
  retyping it).
- **Info-only supporting material at the bottom** — evidence, background, sensitivities
  — clearly separated from the live running order above it.
- **Screenshot-verified before considered done** — Playwright + system Chrome
  (`p.chromium.launch(channel="chrome")`) is the working path in this environment; no
  separate `playwright install` needed. Headless system Chrome
  (`chrome.exe --headless --disable-gpu --screenshot=...`) also works as a fallback.
- **No AI trace anywhere** — text, metadata, alt-text. Same standing rule as the KPI
  decks (`memory/no-ai-fingerprint-on-decks.md`).
- **Never a Claude Artifact.** Standalone HTML file only, saved to the person's
  `output\` folder.
- **The actual submittable PDR form stays `.docx`/`.md` in Oxford's own template
  format where that's the required submission format** (Path B, Kevin's own form) —
  the HTML-only rule governs Lauren's own meeting-prep deliverables (briefs, running
  orders, scripts), not the underlying organisational form itself, which is a real
  Word document required by the PDR process, not a brief.
- If an existing `.md` flow-note is found still live anywhere, retire it: move to
  `archive\<year>\` with a `- superseded-<date>-html-conversion` suffix, and delete any
  stale copy of it that was ever committed to GitHub (check
  `PDR 2026 - Handover/` and similar folders first).

## 5. Folder convention — permanent, not tied to a year folder

```
C:\Users\admin\OneDrive - Nexus365\Meetings\Meetings\PDR\<Name>\
  input\       <- this year's live draft PDR docx (Path A only — the person's own
                   submitted self-review). Path B (Kevin) has no input draft; a short
                   marker note explains why instead.
  output\      <- generated brief + submittable form. Only Lauren writes here.
  archive\
    2024\
    2025\
    2026\      <- prior-year completed PDRs and superseded same-year drafts/briefs
```

This **replaces** the old `PDR 2026\<Name>\` flat layout (input, output, and
`_older versions\` all mixed together in one folder) as of 22 Sep 2026. There is no
`PDR <year>\` folder any more — `PDR\` is permanent, and each year's material sorts
into that person's own `archive\<year>\` as it's superseded. `Template\` sits at the
top level (`PDR\Template\`), not per-person — it's shared reference material, not
person-specific content.

**Sorting rule when a file's status is ambiguous:** never guess from the filename
alone. Check the docx's own `docProps/core.xml` (`created`/`modified`/`creator`/
`lastModifiedBy`) and/or read a content snippet to confirm which year and which
status (submitted draft vs. Lauren-generated form vs. completed prior-year review)
a file actually is before filing it. If it's still genuinely ambiguous after that,
leave it where it is and flag it to Kevin rather than filing it on a guess.

**Special case — a person's current-year draft hasn't arrived yet:** don't fabricate
one. Their `input\` folder should clearly say so (a short marker file, e.g.
`0 - <YYYY> DRAFT NOT YET RECEIVED.txt`), not sit ambiguously empty.

## 6. Standing note — check sources unprompted, every cycle

Don't wait to be told to check Granola, email (Codex connector), command-centre, or
work-inbox each cycle — this is standing, default behaviour, not something that needs
re-instructing per run. This directly parallels the equivalent standing rule already
in force for the Monthly Standing Agenda build (Lauren's `AGENT.md`, "Standing
responsibility: mandatory content sourcing for every Monthly Standing Agenda build",
22 Aug 2026 lineage) — the same discipline now applies to every PDR build, for both
Path A and Path B. If a source genuinely can't be reached (e.g. a connector access
gap), say so plainly in the output rather than silently skipping it.

## Known gotchas (carried forward from the 2026 round)

- **python-docx on SDT-wrapped table cells:** Word sometimes wraps a whole `<w:tc>`
  inside a content-control `<w:sdt>` element. `python-docx`'s normal
  `.text`/`cell.text` API and simple `tr.findall('w:tc', ns)` walks silently miss
  these — the form looks empty/blank when it isn't. Walk `w:tr` children manually and
  look one level into `w:sdt` > `w:sdtContent` for the real `w:tc`.
- **`insert_paragraph_before()` ordering:** calling it twice on the same target
  paragraph inserts in call order immediately before the target
  (`target.insert_paragraph_before(A); target.insert_paragraph_before(B)` →
  `A, B, target`). Check paragraph order after any such call.
- **Bash heredocs break on real English prose** (apostrophes in "Kevin's",
  "team's", etc.) — use the `Write` tool for any script/file body containing natural
  language, not a `cat > file << 'EOF'` heredoc.
- **Em-dash "mojibake" in terminal output is not file corruption** — check the actual
  Unicode code point (`hex(ord(c))`) before concluding a write is broken.
- **These `brief_chrome.py`-templated HTML files are large** (embedded base64 WOFF2
  fonts + crest image) — use `Grep`/targeted Python string search for reading or
  editing them, never a plain full-file `Read`.
- **`gh api -f content=@file` and `-f content=<inline base64>` are both unreliable**
  for anything beyond a trivially small payload (confirmed three separate times —
  silent literal-string sends, "not valid Base64" rejections on genuinely valid
  payloads). Build the JSON payload with a small Python script and push with
  `gh api -X PUT ... --input payload.json`, or use `gh api -F content=@file` (capital
  `-F`, reads the file) as the more reliable single-file alternative.
