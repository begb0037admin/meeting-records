REF Qualification UDF — Knowledge Base Research Brief

Prepared: 6 July 2026 Source: HR FA Knowledge Base (2,226 documents) Scope: Person-level UDF for REFQUALCON outcomes Environment: UOXU (test target)

Purpose

This brief reports on a structured search of the HR FA Knowledge Base to support assessment of the proposed approach of recording REF qualification outcomes (REFQUALCON) using a person-level UDF in PeopleXD, rather than an appointment-level UDF. The search covered seven research areas: UDF configuration, REF/HESA data, multiple appointments, data imports, reporting, and testing guidance.

The upload file is intended to cover Research Only, Teaching and Research Only, and Non-Atypical (Terms 1 or 2) contracts only. Population analysis indicates no individual currently holds more than four qualifying appointments, leading to a draft design with four REFQUALCON fields per person record. Initial testing is targeted at UOXU.

Important caveat The knowledge base contains no documentation specific to REF qualification data, HESA Staff Returns, or research contract eligibility rules. All findings below are drawn from general PeopleXD UDF, import, and reporting documentation. Supplementary guidance from Access Group / PeopleXD support is strongly recommended before testing.

Area 4 — Multiple Appointments

Partial

No dedicated guidance on multiple appointments in a REF or HESA context was found. However, the SQL reporting documentation confirms the underlying data model.

HOW TO — SQL Fundamentals for HR Reporting
Source: Library / ReportingAdded: 18 June 2026
The data model is confirmed as: a person master record in PRBI_HR_PERSON_MASTER joined to appointment records in APPOINTMENT_HISTORY via person_reference. This one-to-many relationship is the structural reason why the choice between person-level and appointment-level UDFs matters.
Key extract — data model SELECT pm.forename, pm.surname, ah.appointment_id FROM PRBI_HR_PERSON_MASTER pm INNER JOIN APPOINTMENT_HISTORY ah ON pm.person_reference = ah.person_reference

A person can have multiple rows in APPOINTMENT_HISTORY. A person-level UDF is stored once against the person record and is always a 1:1 read from the person master. An appointment-level UDF is stored per appointment row.
GitHub library — HOW TO - SQL Fundamentals for HR Reporting.md
HOW TO — Delete Contract (Appointment) within PeopleXD People Management
Source: How To Guides / People ManagementUpdated: 22 September 2022300 KB
Covers deletion and replacement of appointment records where a person has multiple concurrent appointments. Confirms PeopleXD supports multiple appointment sequences per person. Note: if an appointment is deleted or replaced, appointment-level UDF data attached to it is affected; person-level UDF data is not.
SharePoint — HOW TO - Delete Contract (Appointment) within PeopleXD PeopleManagement.docx
Risk — no linkage between person UDF values and specific appointments The proposed design uses four numbered fields (REFQUALCON1–REFQUALCON4) on the person record. Because the fields are positional rather than linked to appointment IDs, there is no system-enforced relationship between a given outcome value and the specific appointment it relates to. This is a design constraint, not a technical barrier — but it must be documented for future maintainers and for any HESA extraction logic.

Area 5 — Data Imports

Found

Import documentation was found. The most important finding is the confirmed limit of 12 UDF columns per import record.

HOW TO — Prepare Data for the Data Migration Tool v2.1 (DRAFT Aug 2021)
Source: How To Guides / System AdministrationUpdated: 4 August 20216,852 KB
Oxford’s primary guide for preparing upload files for the Data Migration Tool.
Key extract — UDF column limit “Your upload file must contain all of the columns shown on the template document even if they contain no data. The upload template will include a column for each possible data item so for a UDF, 12 fields can be added so there will be 12 columns in addition to the required fields. Once you have saved your upload file as a .CSV, DO NOT SAVE again when exiting as the formatting you have just completed will change back to the defaults.”

Implication: Four REFQUALCON fields sits within the 12-field limit. There is headroom to expand to 12 if the population ever exceeds four qualifying appointments, without changing the import mechanism.

Reporting risk — person-level UDF and multi-appointment HESA extract If the HESA staff return extract is built at appointment level (one row per eligible appointment), a person-level UDF with positional fields (REFQUALCON1–REFQUALCON4) introduces a mapping challenge: the extract logic must determine which outcome corresponds to which appointment. This logic is not documented in the knowledge base and would need to be designed and tested specifically. An appointment-level UDF would avoid this entirely.

Recommendations

  • 1Read the PeopleXD UDF Configuration Guide before configuring in UOXU. The vendor guide (PeopleXD People Management- User Defined Field Configuration V1.0.pdf) is in the library and is the most authoritative reference for field types, storage behaviour, and configuration options.
  • 2Raise a question with Access Group on HESA extraction behaviour. The single most important gap is how the HESA staff return extract handles person-level UDFs for staff with multiple appointments. If the extract produces one row per appointment, person-level positional fields create a mapping problem. Ask Access Group this directly before committing to the design.
  • 3Document the appointment-to-field mapping rule explicitly. Whichever design is adopted, the rule for which appointment maps to REFQUALCON1, REFQUALCON2, etc. must be documented in the upload specification and in the UDF Knowledge Article before any data is entered.
  • 4Consider appointment-level UDF as an alternative before testing. An appointment-level UDF stores the outcome directly against the contract it describes, eliminating the positional mapping problem and future-proofing against population changes. The tradeoff is a more complex data entry and reporting model. Formally assess this alternative before UOXU testing begins.
  • 5Prepare a test import file with all four UDF columns before configuring the UDF. The Data Migration Tool requires the full template column set even for empty fields. Prepare the CSV with four REFQUALCON columns and a small sample of test records before the UOXU configuration session.
  • 6Raise an OSM Change Request before promoting from UOXU to production. Category: Configuration; Justification: Enhancement. Section 8 (Testing) should specify the acceptance criteria. Section 14 (Back-Out Plan) should confirm UDF deletion and data re-import as the rollback path.
